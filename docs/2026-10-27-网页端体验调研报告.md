# 网页端体验调研报告（2026-10-27）

> 范围：网页端（React 18 + TS + antd5 + Tailwind + Vite5）+ 后端 API（Django 4.2 + DRF）。
> 不含：模型与训练、小程序、桌面端。
> 性质：体检表，不是改造单。改造顺序见 `plans/2026-10-27-网页端体验收尾分批计划.md`，视觉口径见 `docs/2026-10-27-设计系统基线.md`。
> 所有数字为 2026-10-27 本机实测（dev 库 + 本地生产构建 + 线上站点只读探测），未使用估算值。

## 1. 五条结论

1. **视觉方向已经统一，设计系统仍是两套。**
   `src/index.css` 头部写「HeroUI 口径」，主色 `--brand-fill: #0070e0`；`src/tailwind.config.js` 头部仍写「iOS 26 Liquid Glass 磨砂玻璃体系」，主色 `#0a84ff` + `backdropBlur 28px`。两套色板同时在跑：`src` 内硬编码十六进制色 **656 处**、`bg-white` **199 处**、`glass` 相关 18 处。
   直接后果可量化：`#0a84ff` 白底对比度 **3.65:1**（不过 AA 4.5），`#0070e0` 是 **4.78:1**（过）。axe 报的 58 个对比度节点，一部分就是这套双基线造成的。

2. **移动端不存在破版。**
   12 页 × 4 档宽度（1600/1280/768/390）+ Chromium/WebKit 双内核：横向溢出 **0**。原先担心的手机、平板塌版可以撤掉。
   但 390 下图片管理左栏（文件夹/未归类/与我共享）整块消失且没有抽屉入口——不是溢出问题，是**功能不可达**。

3. **性能债在资源，不在代码量。**
   首页 Lighthouse 总传输 **8,076 KiB**，其中 **6.35 MB 是三张未压缩 PNG 横幅**（2.10 / 2.05 / 1.95 MB）。
   线上静态资源**不带 gzip、也没有 Cache-Control**（见 §2.4）；Lighthouse mobile 机会项里 uses-text-compression 估省 **5.1s**。
   首屏 gzip **411.9 kB**，其中 ui-kit 单 chunk **281.2 kB**，占 68%。

4. **三条必须当 P0 处理的硬缺陷。**
   ①`/api/oss/` 缺对象归属校验：登录用户可 `GET`/`DELETE`/枚举他人任意对象（匿名被全局 IsAuthenticated 挡在 401，**不是**匿名可读删；已于 `159f4d6` 修复）。
   ②`.env` 里生产库/OSS/邮箱明文凭据躺在源码目录，且项目无 `.git` 也无 `.gitignore`。
   ③仓库里的 `nginx.conf` 与线上实际配置不一致（线上有 `/api` 反代，仓库里没有）——部署不可复现。

5. **两条流传的说法要纠正，避免错误排期。**
   ①「每张图都重复 torch.load 模型」**不成立**：`predict/services.py` 的 `load_model` 有 `self.models` 缓存，且模块级单例 `deeplabv3plus_service`。真实残留问题是缓存键只有路径、没有 mtime/版本，换权重必须重启进程。
   ②「后端只跑 runserver」只是这台开发机的形态；线上有 nginx/1.24.0 在反代 `/api`（应用服务器类型未确认）。真实缺口是**部署配置没进仓库**，不是「没上生产服务器」。

## 3. 问题清单

### P0 —— 安全、配置、可复现性（不做完不建议对外）

#### P0-1 `/api/oss/` 缺少对象归属校验，任意登录用户可读删他人对象（已修复）
- 证据：`predict/urls.py:63` `path('oss/', csrf_exempt(views.OssObjectView.as_view()))`；`predict/views.py:1343` 起 `OssObjectView` 未声明 `permission_classes`，`get()` 支持 `?key=` 直出二进制或按 `prefix` 列清单，`delete()` 支持 `?key=` 直删。
- 实测口径（2026-10-27 修正）：全局 `DEFAULT_PERMISSION_CLASSES = IsAuthenticated` 生效，**匿名请求实际返回 401**，不存在「匿名可读删」；真实风险是**横向越权**——任意已登录用户可 `GET`/`DELETE` 他人任意 key、可 `prefix` 枚举整个桶。实测：新用户 `qa_probe` 对他人对象 `GET` → 200、`DELETE` → 200 且对象真实消失、`LIST` → 200。
- 影响：任何普通账号（含访客账号）都能遍历下载全库图片、删除他人数据。
- 处置（提交 `159f4d6`，分支 `fix/oss-auth`）：新增 `_oss_key_owned_by()`，key 必须属于本人名下的 `CassavaImage`/`SegmentationResult`/`PredictionResult` 记录或调用者为管理员；`GET`/`DELETE` 走归属校验，`GET` 列前缀限管理员，`POST` 显式 key 时禁止覆盖他人已有对象。复测：匿名 401；跨用户 GET/DELETE/LIST/覆盖 403；本人 200。

#### P0-2 生产凭据明文落盘
- 证据：`网页\back\cassavaBack\.env` 含 `DEBUG=False`、远程 PostgreSQL（`8.148.197.199:5432`，库 `test`，用户 `cassava`）、OSS 密钥、163 邮箱密钥；项目**无 `.git`、无 `.gitignore`**。
- 影响：当前没泄漏是因为没进版本库；一旦 `git init` + 推送或打包分发，凭据直接外泄。而计划第一批就要 `git init`——所以必须先处理。
- 建议：先轮换，再拆分 `dev.env` / `prod.env`，密钥只走部署环境变量；仓库存 `.env.example`。

#### P0-3 部署配置与线上不一致
- 证据：仓库 `网页\front\cassava_front\nginx.conf` 46 行，只有 `gzip on;`（无 `gzip_types`）、SPA `try_files`、`/50x.html`，**无 `location /api`、无 `client_max_body_size`**；线上实测 `/api/*` 正常反代。
- 影响：看仓库复现不出线上；改仓库的 nginx 也不影响线上。大图上传在线上是否被 413 拦住**未验证**（线上上传接口未探测）。
- 建议：把线上实际 nginx 配置回收进仓库（脱敏），两边对齐后作为唯一部署源。

#### P0-4 静态资源不压缩、不缓存
- 证据：见 §2.4，JS/CSS 无 `Content-Encoding`、无 `Cache-Control`。
- 影响：首屏 1.3 MB JS 全量传输且不可复用缓存，移动网络下直接 3–8s 白屏。
- 建议：`gzip_types text/css application/javascript application/json image/svg+xml`；`dist/assets` 加 `expires 1y` + `immutable`（hash 文件名已具备条件）；`index.html` 保持 `no-cache`。

#### P0-5 无版本控制
- 证据：项目根与 `网页\` 下均无 `.git`；历史靠 `tasks\<日期>-*.md` 与备份目录。
- 影响：无法回滚、无法 review、无法分叉实验；也是 P0-2 不敢动的原因。
- 建议：`git init` + 一次性 `.gitignore`（`node_modules/`、`dist/`、`.env`、`*.pth`、`*.pt`、`media/`、`db.sqlite3`）+ 首提交快照；此后用分支替代备份目录。

### P1 —— 体验与一致性（「无破绽」的主体工作量）

#### P1-1 设计系统双基线未收口
- 证据：`src/index.css`（425 行）HeroUI token 齐全；`src/tailwind.config.js`（113 行）仍以 `ramp(#0a84ff…)` 生成 Liquid Glass 色阶 + `glass` 阴影 + `backdropBlur 28px`；`src` 内硬编码 hex 656 处、`bg-white` 199 处、`glass` 18 处、`backdrop-blur` 5 处；三套 UI 来源并存（antd 13 文件、lucide-react 16 文件、@headlessui/react 1 文件 + 自研组件）。
- 影响：任何一次视觉统一都会被绕过 token 的地方打断；对比度失败项、圆角/阴影不一致都从这里来。
- 建议：以 `docs/2026-10-27-设计系统基线.md` 为准，先冻结 token，再逐页替换硬编码；`--radius-lg` 与 `--radius-xl` 同为 16px 属重复，收敛为一个。

#### P1-2 页头骨架不统一
- 证据：图片管理、任务中心的标题在卡片内；PPD 预测页的「PPD预测」在卡片外。左栏「第9天-250张」与「(250)」折行错位，选中胶囊样式与「所有图片(280)」不一致。
- 建议：统一为「页头区（标题+副标题+主操作）→ 内容卡」两段式，全部页面套同一组件。

#### P1-3 图片管理页的局部缺陷
- 证据（截图逐项）：左栏「新建文件夹」主按钮 + 根目录下拉 + 输入框 +「创建」挤在一行，创建按钮被压扁；左栏有第二个「搜索图片」与主搜索重复；工具栏「按日期排序」「按年分组」两个下拉 + 一个无名图标按钮；右上「格/列表」切换器浮在卡片外、压到内容右缘；右侧游离一个「2026」年份标签，与分隔线里的 2026 重复；390 下左栏消失且无抽屉入口。
- 推荐：左栏只留文件夹树；「新建文件夹」改为弹窗；搜索只保留一处；排序/分组/视图切换收进一个工具条；<768 左栏转抽屉。

#### P1-4 首页信息与排版
- 证据：H1「木薯采后腐烂面积智能预测系统」在 1600 下折成「…预测」+「系统」孤行；统计条四张卡口径混乱（「11418+ 总访问量」「独立验证中·精度评估」「2+ 预测功能使用次数」「35+ 预测图片总数」，把非数字当数字摆）；hero 卡底部大片留白。
- 建议：H1 限宽或 `text-wrap: balance`；统计条只保留真实可解释的三个数（访问量、处理图片数、预测任务数），「独立验证中」改成状态标签挪出数字位。

#### P1-5 任务中心可读性
- 证据：右上一排胶囊（总任务/已完成/运行中/失败/成功率）字号 <12px 且过挤（该页 12px 以下文本 10 处，全站最多）；进度条满宽亮蓝视觉权重过大；行内元信息「投票模型 5张 2026/10/23 15:58:16 53秒」同字号同灰度；删除为红色图标按钮**无二次确认**；标题旁蓝圆「A」图标疑似错字。
- 建议：胶囊改 12px 起并降为次要样式；进度条降不透明度；元信息分主次两档灰；删除加重确认；图标换语义正确的。

#### P1-6 结果中心细节
- 证据：任务标题「预测任务-2026/10/2…」截断；图上 PPD 深色浮标仍是玻璃风残留（与白卡基线冲突）；「投票评分」呈灰胶囊、可点性不明。
- 建议：标题两行或省略中间；浮标改实底白卡+边框；可点元素补 hover/焦点态。

#### P1-7 无名按钮与表单标签
- 证据：无名按钮 94 个（`<button>` 182 / `aria-label` 23）；axe `button-name` 132 节点、`label` 97 节点、`select-name` 5 节点。
- 建议：纯图标按钮一律 `aria-label`（或引入统一 `IconButton` 组件强制该 prop）；表单用 `<label htmlFor>` 而不是占位符。

#### P1-8 8 个指向不存在端点的调用
- 证据：`src/services/api.ts:364` `GET /images/days/`、`:365` `/images/types/`、`:399` `POST /segmentations/first_segmentation/`、`:429` `/predictions/predict_single/`、`:430` `/predictions/predict_batch/`、`:449` `/tasks/first-segmentation/`、`:450` `/tasks/second-segmentation/`、`:451` `POST /tasks/prediction/`——后端 `predict/views.py` 的 `@action`（188/489/702/745/768/911/945/990/995/1094/1102/1279/1295/1301/1307/1336）无一对应。
- 影响：不是「潜在 bug」，是明确死代码 + 一旦有人调用就 404。
- 建议：删除或改为调用真实端点；配合 TS 契约测试防止再长出来。

#### P1-9 创建任务时不做参数校验
- 证据（实测）：POST `/api/tasks/` 传 `algorithm='deeplabv3plus_resnet101'`（非法 key，合法值是 `resnet101/resnet50/mobilenet/m6_best/ensemble`）→ **201 创建成功**，随后异步失败，前端只看到「任务执行失败，请重试或联系管理员」，真实原因 `不支持的预测模型` 只在服务端日志。
- 影响：用户拿到无信息量的失败；也说明「任务中心失败率高」的观感可能来自参数就错。
- 建议：`create()` 里校验 `single_model_type∈DEEPLAB_MODEL_CONFIGS/MEMBERS`；失败原因写入 `task.error` 并在前端展示。

#### P1-10 失败态无诊断信息
- 证据：同一实测里 `task.error` 落的是通用文案；`error_code`/`error_message` 在结果对象上存在但任务层没用起来。
- 建议：任务层落 `error_code`+可读原因+「重试」入口。

### 多人化（组织内多用户，非多租户）
现状：`predict_cassavaimage` 等表已有 `owner` 字段，但列表查询未按人过滤；`AuthToken` 单 token（每次登录换发，旧 token 是否失效未验证）。
落地顺序：数据归属字段齐备 → `get_queryset` 按 owner/组过滤 → 组模型 → 多会话 token。**不做**配额、计费、跨端同步。

## 4. 本轮不做（显式非目标）

1. 不做真多租户（独立库/schema 隔离），只做组织内多用户 + 数据归属。

## 6. 闭环实测（dev 环境真跑一次预测）
