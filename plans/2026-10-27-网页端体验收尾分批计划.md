依赖理由：
- 批次 0 必须最先，否则首提交会把 `.env` 明文凭据一起提交（且没有 `.gitignore` 拦不住 `*.pth` 451MB）。

- 批次 4 在批次 3 之后：性能优化要动 token 与图片资源，先定稿视觉再压体积。
- 批次 5 可与 3/4 交错，但 CI 必须在批次 1 之后（要先有 git）。
- 批次 6 必须最后：3,873 行的拆分没有测试兜底就是纯风险。

## 批次 2 · 多人化前提（组织内多用户）

**目标**：数据归属到人/组，列表按人过滤；不做多租户、不做配额。

| # | 动作 | 验收标准 |
|---|---|---|
| 2.1 | 审计归属字段现状：`predict_cassavaimage` 等表已有 `owner`，确认所有业务实体都具备 `owner_id`（含 `folder`、`prediction_result`、`segmentation_result`、`processing_task`、`export`） | 输出一张「实体 × 归属字段」表；无归属字段的实体补 migration（只加字段，不改现有结构） |
| 2.2 | 组模型：`Group` + `Membership(user, group, role)`；资源归属为「owner 或 group」 | 建组、加人、移人可用；migration 通过；老数据 group 为空（视为 owner 私有） |
| 2.3 | 所有列表查询按可见性过滤：`owner=self` 或 `group in my_groups` 或管理员；覆盖 `images/folders/segmentations/predictions/tasks/shares` 六个 router + 权限类 router | 用两个账号 A/B 实测：A 建的资源在 B 的列表里 0 条；B 直接 GET A 的资源 id → 403；管理员可见全部 |
| 2.4 | `AuthToken` 多会话：不再「每次登录换发并踢掉旧 token」，改为“每次登录新增一个未被吊销的 token”，支持在多端同时登录 | 同账号两个客户端各自登录后都能持续访问；`POST /api/auth/logout/` 只吊销当前 token；token 表可查登录设备与时间 |
| 2.5 | 权限矩阵回归：现有 `predict_permission` 42 条、`predict_role` 3 条在新过滤下仍生效 | 现有 3 个测试账号（`test` / `qa_normal` / `qa_disabled`）权限行为与改造前一致，`qa_disabled` 仍被拒 |

**验收口径**：一次「A 建图 → B 登录看列表 → B 猜 id 直取」的端到端脚本，结论必须是「0 条 + 403」。
**回滚点**：2.1 只加字段不动结构，可单独回滚；2.3 是行为变更，回滚即恢复不按归属过滤。

### 批次 2 实测校正（2026-10-27 执行后回填）

原计划基于「列表没过滤、需要新加 owner」的假设，实测后三条假设被推翻，工作量比预估小得多：

| # | 原计划 | 实测结论 |
|---|---|---|
| 2.1 | 审计归属字段，缺的补 migration | **已具备，无需改造**。`predict/models.py` 的 `BaseModel` 自带 `owner`（FK User, null=True）；`CassavaImage.oss_key/preview_oss_key`（:185-186）、`SegmentationResult.oss_key`（:250）、`PredictionResult.oss_key/cassava_mask_key/rotten_mask_key/confidence_map_key`（:280-283）均在 |
| 2.2 | 新建 `Group` + `Membership` 模型 | **不新建**。权限已经走 `Role`(3) + `Permission`(42) + `UserRole` 体系，共享走 `ResourceShare`（当前 0 行）；再加一套 Membership 会与现有权限系统打架 |
| 2.3 | 六个 router 补 owner 过滤 | **已生效**。`CassavaImageViewSet.get_queryset` 走 `filter_queryset_by_permission`（`predict/views.py:95-110`）；实测 `qa_normal2`（普通用户角色）看到 images/folders/tasks/predictions 全部 0 条，越权取他人图片详情 404、删除 403，管理员 281 条 |
| 2.4 | 同账号多 token | **已实现，但换模型**：DRF `Token.user` 是 OneToOne（DB 层 UNIQUE），无法多行，故新建 `predict.models.LoginSession`（`key` 40 位十六进制主键 + `user` FK + `created` + `last_seen`），`ExpiringTokenAuthentication.model = LoginSession`，对外仍是 `Authorization: Token <key>`，前端与小程序零改动 |
| 2.5 | 权限矩阵回归 | **43 tests OK**（原 38 + 新增 `predict/tests/test_auth_sessions.py` 5 条） |

2.4 的落地细节：登录改为签发新会话并按 `MAX_SESSIONS_PER_USER`（默认 5，可经 env 覆盖）裁剪最旧会话；登出只吊销当前请求的会话（原 `AuthToken.objects.get(user=...)` 在多 token 下会抛 `MultipleObjectsReturned`）；超时判定从「用户级 last_activity」改为「会话级 last_seen」，手机闲置超时不再连带踢掉电脑；迁移 `0038_loginsession` 建表、`0039_purge_legacy_authtoken` 清空历史 `authtoken_token` 残留凭据（升级后所有端需重新登录一次，令牌本身 30 分钟无操作即过期，影响很小）。
